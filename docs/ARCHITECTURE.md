# 架构说明

## 确定性边界

求值器的输入只有：

- 规范化工程内容；
- 调度参数（窗口、预览 FPS、容差、模式策略）；
- 逻辑帧号。

所有 map 输出在写入结果前经过排序；同刻 cue 使用显式业务优先级和稳定 ID 规则；灯光、分组、窗口、cue 结果均有固定顺序。因此工作线程数量、任务完成次序和 SQLite 恢复位置不进入输出哈希。

`ContentHash` 排除真值与运行时资源参数，仅覆盖灯具、分组、变化点、场景、FPS、时长和窗口。`ParamVersion` 覆盖会影响输出的窗口、预览策略、阈值、容差、强制模式和算法版本；并行度与内存预算只影响资源调度，不使检查点失配。

## 求值器

`pkg/stage.NewEvaluator` 将每个 cue 展开成“灯 × 字段”的事件流。每个字段事件在构造阶段预计算：

- 逻辑时间；
- 起始值；
- 目标值；
- 过渡时长；
- 缓动与幂；
- 来源（单灯/分组）及完整排序键。

同一时刻的一批事件共享“批次前值”，最终以业务优先级最高的目标作为该时刻后的活动过渡。帧查询只需在该字段事件序列上二分查找，避免每帧重复扫描全部 cue。

RGB 输出是原始混色、有效亮度与色温 tint 的组合：

```text
t = clamp((kelvin - 2000) / 8000, 0, 1)
tint = (1 - 0.25t, 0.72 + 0.18t, 0.45 + 0.55t)
strobe_gate = phase < 0.5 ? 1 : 0
```

真值生成器使用独立的参考事件重放实现，避免窗口调度器直接生成自己的期望值。

## 调度器

每个窗口是独立纯计算任务。Runner 负责：

1. 打开检查点并校验全局版本；
2. 用连续已提交窗口初始化状态机；
3. 受并行槽位与未提交窗口背压约束地投递窗口；
4. 按窗口号公平获取内存预算；
5. 按窗口号等待结果，只接受连续提交；
6. 通过单一串行事务写检查点；
7. 取消时保留已提交边界。

资源管理有两个层次：

- `inflight` 信号量限制未提交任务数；
- `memoryBudget` 用最小窗口号优先的等待队列防止后序窗口抢占内存。

窗口调度开始顺序也由逻辑窗口号门控，保证并行计算不等于乱序启动。

## 检查点

SQLite 表：

- `checkpoint_meta`：工程级版本与窗口数；
- `checkpoint_windows`：每窗口 JSON payload。

每窗口事务同时检查最后已提交窗口号，防止乱序写入。恢复时检查：

- 内容哈希；
- 参数版本；
- 算法版本；
- 窗口总数；
- 窗口号连续性；
- payload 内版本标记。

任一失败即在同一串行锁内删除该工程整体快照，Runner 从窗口 0 全量重算。显式编辑重定基只在调用方证明编辑不影响已提交时间范围后使用，并且不修改已冻结帧值，只更新版本标记。

## 三路径比对

`VerifyThreePaths` 使用三个独立 SQLite 文件：

1. 实时：一次运行并逐窗口提交；
2. 恢复：运行到中点后停止，再加载同一检查点续跑；
3. 全量：清空检查点后从窗口 0 一次重算。

三条路径的 frame 序列压平后逐帧比较，再比较每窗口 cue offset 与提交序列。首个差异构造 `E_DIVERGE`，定位字段为：

- `frame`：首个不一致帧号；
- `light_id`：灯具标识；
- `field`：具体差异字段，如 `rgb.r`、`pan`、`cue_offset`、`commit_order`。

## Wails 服务层

`App` 在内存中持有当前工程和求值器，负责：

- 生成、加载、保存；
- 参数更新与模式预览；
- 同步调度和暂停；
- 当前帧、时间轴、窗口明细查询；
- 编辑变化点/分组；
- 已提交边界保护；
- 检查点显式作废或版本重定基；
- 三路径验证。

Wails 桌面入口是默认构建目标，前端静态资源通过 `go:embed` 打包。`headless` build tag 可跳过桌面链接，保留 CLI 与领域核心，便于 CI。
